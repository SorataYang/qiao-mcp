# Qiao-MCP 0.5.0

Qiao-MCP 0.5.0 adds typed model queries, transversal live-load definitions,
complete reinforcement/check snapshots and international live loads for supporting
QiaoTong builds. It includes all changes since 0.3.3; there is no separate 0.4.0 release.

The MCP catalog contains **153 tools**, **151 output schemas**, **7 resources** and
**5 workflow prompts**. The server starts and exposes its catalog without a running
QiaoTong desktop; model operations require the connected desktop and an allowed model state.

## Highlights

- Server-side filtered queries and read-only edit-readiness diagnostics.
- Explicit live-load system and operation-stage settings, complete transversal
  vehicle/lane/case definitions, actual-ID readback and verified full result names.
- Full model reinforcement, stirrup, material and check-case snapshots, including
  explicit replacement, deletion and reference semantics.
- AASHTO, BS and EN1991 vehicle definitions, EN1991 factories and planned lanes.
- qtmodel 2.9 support, corrected nodal-mass fields and concrete-check completion
  handling, plus clearer guidance for tools with similar names.

## Upgrade from 0.3.3

`add_nodal_mass` no longer accepts `mass_rm`. Use `mass` for equal translational
mass, optional `mass_x`/`mass_y`/`mass_z` for individual directions, and
`rot_x`/`rot_y`/`rot_z` for rotational inertia. Choose the intended axis rather
than mechanically renaming the old field. Updating the package does not repair
mass values previously written into a model.

Dependencies remain `qtmodel>=2.6.3,!=2.9.0,<2.10` and `mcp[cli]>=1.29,<2`.
One-shot bridge workflows need qtmodel 2.6.4 or later because 2.6.3 lacks
`get_load_group_names`. New features also require the corresponding desktop API.
See the [migration guide](../README.md#upgrading-from-033).

## Known QiaoTong limitations

Live testing used QiaoTong **26.1.116.1010** and qtmodel **2.9.2**. Basic cantilever
reactions, moments and translations matched the hand calculation, and the tested
B1 queries and state guards passed. This is partial engineering coverage.

- `GET-DEFORMATION` returns an incorrect Rz in this desktop build, despite the
  correct value in the solver database. Do not rely on the API Rz from this build.
- The desktop rejects `clear_existing` during live-load system selection. The
  transversal workflow is blocked, and the international workflows sharing that
  prerequisite were not run.
- `SET-SECTION-REINFORCEMENT`, `SET-CHECK-STIRRUP` and `SET-CHECK-CASE` return
  Unknown command. The full B3 snapshot/check workflow remains unverified.
- BS axle-force units are still undocumented upstream; preserve verified native
  export/query values without converting units by analogy to another code.

Connection compatibility is not feature acceptance. These limitations require a
supporting QiaoTong build and further testing; the client does not bypass them or
invent engineering results. Reproduction details are in the
[live-test report](0.5.0-live-validation.md).

## Validation

The offline compatibility matrix passes in full on PyPI qtmodel 2.9.2 and source
`0687ffe`. Older builds retain explicit feature skips, and the two existing
qtmodel 2.6.3 contract failures remain documented.

Release checks cover versions, source/package contents, runtime dependencies,
MCP initialization, tool schemas and error responses. The full record is in
[offline validation](0.5.0-validation.md); the final candidate checks and package
hashes are recorded in [release preparation](0.5.0-release.md).

## Install

After the version is available on PyPI:

```bash
uvx --from qiao-mcp==0.5.0 qiao-mcp
```

Use `check_qiaotong_connection` and `get_model_status` before model operations.
Cross-machine SSH connections use `http://localhost:45125/pythonForQt/`, preserving
the Host name accepted by the Windows API.
