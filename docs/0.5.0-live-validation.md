## 基础悬臂梁与数值核对

在 `cantilever-static.bfmd` 中建立 X 向 10 m 悬臂梁，使用 N、m 单位：

- 节点 1001、1002、1003 分别位于 `(0,0,0)`、`(5,0,0)`、`(10,0,0)`。
- 梁单元 2001、2002 分别连接 1001→1002、1002→1003，节点 1001 六自由度固定。
- 材料 ID 1 为 C50，截面 ID 1 为 1 m × 1 m 矩形，包含剪切变形。
- 工况 `MCP_TIP` 在自由端施加 `Fz=-10000 N`；显式运营列表仅包含此静力工况，
  沉降、纵向活载和横向活载列表为空。关闭施工阶段、徐变和自振计算。

实际回读 `E=34,500,000,000 Pa`、`G=14,375,000,000 Pa`、
`Iy=Iz=0.083333341654 m⁴`、剪切面积 `Ay=Az=0.82821684 m²`。
以这些回读参数计算自由端位移：

```text
Dz = Fz·L³/(3·E·Iy) + Fz·L/(G·Az)
   = -0.001159420174089287 - 0.000008399396635222286
   = -0.0011678195707245094 m
```

| 核对量 | 手算 | 桥通实际返回 |
|--------|-----:|-------------:|
| 支座 Fz / N | 10000 | 10000.00000000003 |
| 支座 My / N·m | -100000 | -100000.00000000015 |
| 单元 2001 根部 My / N·m | -100000 | -100000.00000000015 |
| 自由端 Dz / m | -0.0011678195707245094 | -0.0011678050118558224 |

含剪切变形的位移相对差为 **0.0012467%**，约 0.00125%。
求解完成状态、反力平衡、根部弯矩和上述位移均已用保存的数据核对。
这只验证该基础算例中的这些量，不包含下面已发现错误的 `rz`。

另在 `cantilever-rotations.bfmd` 中添加正交工况 `MCP_TIP_Y`，自由端施加
`Fy=10000 N` 并重新求解。端部 `Dy=0.0011678050118558224 m`，
支座 `Fy=-10000.00000000003 N`、`Mz=-100000.00000000015 N·m`，与受力一致。

## 问题一：服务端变形接口的 Rz 错误

竖向工况 `ST:MCP_TIP`、节点 1003 的同一次求解结果如下，转角单位为 rad：

| 数据来源 | Ry | Rz |
|----------|---:|---:|
| 原始 HTTP `GET-DEFORMATION`，以及 MCP 返回 | 0.00017391302956521962 | 0.00017391302956521962 |
| 求解 SQLite `NodeDisplacement` | 0.00017391302956521962 | -1.2975126271805935e-17 |

该工况只应产生绕 Y 的弯曲转角，求解文件中的 Rz 接近零，符合模型受力。
HTTP 的其余五个变形分量与该数据库行完全一致，只有 Rz 不同。
正交工况又返回 `ry=rz=-1.2975126271805927e-17`，尽管其绕 Z 弯曲应有非零转角。

问题已经出现在绕过 qtmodel 和 MCP 转换的原始 HTTP 响应中。
qtmodel 的 `odb.get_deformation` 和本项目 Provider 均直接传递该结果；
当前证据将问题定位在服务端结果接口，具体实现修复仍需桥通端确认。
本轮没有在 MCP 端猜算、交换或填补转角。

复现时打开保存的 `cantilever-static.bfmd`，在桥通中进入运营阶段后处理并加载
同目录的求解结果，再发出只读请求：

```python
import json
import requests

session = requests.Session()
session.trust_env = False
response = session.post(
    "http://localhost:45125/pythonForQt/",
    headers={"Content-Type": "GET-DEFORMATION"},
    data=json.dumps({
        "ids": [1003],
        "stage_id": -1,
        "case_name": "ST:MCP_TIP",
    }).encode(),
    timeout=(3, 8),
)
response.raise_for_status()
print(response.json())
```

只读打开 `Brdi3DBridge_cantilever-static/cantilever-static_001.ard` 后可对照：

```sql
SELECT NodeId, Dz, Ry, Rz FROM NodeDisplacement WHERE NodeId = 1003;
```

该结果文件 SHA256：
`26e9933cb43c6343b7683c56a19b97563b51afec50e9ce888751a5d556022d38`。
原始 HTTP 响应、SQL 行及请求参数均保存在实测证据 JSON 中。

## 问题二：B2/B4 的体系设置前置条件不满足

在未求解的独立 `transversal.bfmd` 中调用：

```json
{
  "tool": "configure_live_load_system",
  "arguments": {"system": "china_transversal", "clear_existing": false}
}
```

实际返回 MCP 错误：

```text
Error configuring live-load system (设置活载体系失败): 未知参数：clear_existing
```

客户端存在该参数，服务端仍拒绝它。未删除参数后重试，未改用可能改变清理语义的旧调用。
随后横向车辆、车道和工况的只读查询均成功返回空，但没有定义对象或运行横向求解。

B4 也依赖此体系设置契约，因此 AASHTO、BS、EN1991 的完整链路均未开展；
不能把这一结果写成三种规范的车辆接口已经逐一实测失败。
三个 `international-*.bfmd` 只是未求解模板副本，没有打开验收。

## 问题三：B3 三条快照命令不被识别

| MCP 工具 | 服务端拒绝的命令 |
|----------|------------------|

| `set_check_stirrup_snapshot` | `SET-CHECK-STIRRUP` |
| `manage_check_case_definition` | `SET-CHECK-CASE` |

并在 `Actual value was ...` 中标明对应命令，没有成功提交快照。
完整请求和错误保存在证据 JSON。

探针以仓库原生导出 fixture 的完整字段为基础，替换为当前测试材料及名称：
截面实际钢筋点位于轮廓内部，箍筋保留原生存储单位和零值字段。
检算工况引用真实存在但尚无单元的默认结构组，仅用于命令接口探测。
这些输入不构成已完成的工程配筋设计。

失败前后各通过桥通原生接口导出一次模型，两个文件均为 2555 字节，


仅进行了文本/AST 解析，未执行。没有将旧 CSAN 查询冒充基础模型完整快照。
由于箍筋定义未成功，未继续单元配箍；完整材料覆盖、撤销/重做及混凝土检算也未开展。
